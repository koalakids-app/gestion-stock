## Règles métier de la commande repas traiteur (MCM)
- Le comptage vient d'une source unique : `crCountsParJour` (`js/pages/demandes/06-export-direct.js`), utilisée par le bon et par le rappel des effectifs (`mcmCmdRenderEffectifs`, `04-filtre-presents-uniquement.js`).
- Exclus du bon : enfants au biberon (BIB), **goûter crèche** (`enfants.gouter_base = 'creche'`, uniquement le goûter), **PAI actif avec panier repas** (repas et goûter).
- Aucun goûter avant 6 mois ; le régime SV n'existe pas au goûter.
- Ligne du bon : le code repas décide, pas l'âge (`mcmLigne`) — BB → « Bébés − de 6 mois », M → « Bébés 6-18 mois », G → « Grands » (ou périscolaire à partir de 48 mois).
- Repas BB (légumes sans protéines, avec ou sans régime) : goûter compris dans le repas, donc aucun goûter ; le goûter « bébé » (`gbb`) s'appelle désormais « goûter moyen » à l'écran.
- Le PAI se saisit **dans le registre de soins** (`infirmerie.html`, table `pai`, case « Panier repas »). La fiche enfant le **lit** (`enfPaiCharger`, `enfPaiPanier` dans `js/enfants/01-core.js`), elle ne le modifie pas. Un PAI clôturé remet l'enfant dans la commande.

## Menu du traiteur par QR code
- `menu.html` (page publique, sans compte) lit la fonction `menu_public(date)` (`sql/menu_public.sql`, à appliquer à la main) : une seule semaine, colonnes d'affichage uniquement. Le QR se génère dans MCM › Menus (`mcmMenuQr`) ; version « permanente » sans date = semaine en cours.
- Goûters faits par la crèche : table `menus_gouters_creche` (`sql/menus_gouters_creche.sql`, à appliquer à la main ; accès via `kk_acces_creche`), deux textes par crèche et par jour (`gouter` = moyens, `gouter_grand` = grands ; `sql/gouters_creche_moyen_grand.sql`), qui remplacent `bb18_gouter`/`grand_gouter` du traiteur pour cette crèche (`js/pages/demandes/13-gouters-creche.js`). `menu_public(date, crèche)` fusionne les deux ; le QR d'un référent porte `?c=<id crèche>`.
- Goûter moyen : deux lignes par jour (produit 1 / produit 2, texte stocké « a / b ») avec un effectif chacune (`gouters_creche_effectifs.moyens_l1`/`moyens_l2`, `sql/gouters_creche_moyens_lignes.sql`, à appliquer à la main ; `moyens` = le plus grand des deux).
- Le titre des recettes choisies s'affiche sur le menu du jour : `gouterCrecheMap` lit `gouters_creche_recettes` (champs `rm`/`rg`, assemblés par `gouterAffiche`) et `menu_public(date, crèche)` est redéfinie dans `sql/gouters_creche_recettes_menu.sql` (à appliquer à la main, après les autres versions).
- Option « cette crèche fait tous ses goûters » : table `gouters_creche_options` (`sql/gouters_creche_option_tous.sql`) ; jour vide = aucun goûter affiché, et `crCountsParJour` ne compte aucun goûter pour cette crèche (`gouterTous`).

- Recettes des goûters : tables `recettes`, `recettes_ingredients`, `gouters_creche_effectifs` (moyens/grands par jour), `gouters_creche_recettes` (`sql/recettes_gouters.sql`, à appliquer à la main). Recettes communes aux crèches (écriture direction via `kk_est_direction()`), allergènes par ingrédient. Logique et récapitulatif 2 semaines dans `js/pages/demandes/14-recettes-gouters.js` (`gcLignes` calcule les produits à commander).

- Idées recettes pour les parents : bouton « Idées recettes » de MCM › Menus (`irfOuvrir`, `js/pages/demandes/22-idees-recettes-familles.js`) ; recettes de la bibliothèque mises à l'échelle (portions), fiche A4 imprimable, texte à copier, ou publication dans `famille_messages` + push (`mfPrevenir`). Pas de SQL.

- Guide de la diversification : synthèse en dur du guide de Santé publique France dans `js/pages/demandes/17-guide-diversification.js` (`GD_TRANCHES`, `GD_CRECHE`), bouton « Guide diversification » de MCM › Menus.

## Espace famille
- Page publique `espace-famille.html` (`js/pages/espace-famille.js`) : le parent saisit un code à 8 caractères (ou ouvre `?t=<code>`), lit les informations de la crèche, retrouve le **code image de pointage** de l'enfant (`enfants.code_pictos`, 4 images dans l'ordre, jamais le code numérique), retrouve le lien du suivi (`suivi_acces_famille`) et dépose des documents. Tout passe par l'edge function `espace-famille` (`--no-verify-jwt`, ajoutée à `deploy-functions.yml`) ; 10 codes faux / 15 min par IP bloquent (`famille_essais`).
- Tables `famille_acces` (un accès par enfant et par parent, révoqué jamais supprimé), `famille_messages`, `famille_messages_lus`, `famille_essais` : `sql/espace_famille.sql`, à appliquer à la main. Dépôts = `enfants_documents_admin` (`piece_key` `espace_famille:<libellé>`) + `signalerDepot`.
- Création automatique : déclencheurs SQL sur `contrats` (statut `signe`/`contresigne` + `enfant_id`) et `enfants_parents` (`sql/espace_famille_creation_auto.sql`, à appliquer après `espace_famille.sql`, rattrape les contrats déjà signés) ; jamais de recréation d'un accès révoqué. Le code part par e-mail avec le contrat signé (`envoyer-contrat-signe`, un message par adresse, code retrouvé par l'e-mail du parent).
- Documents de l'espace : devis et contrat signé en PDF (`famille_documents` + bucket privé `famille-docs`, `sql/espace_famille_documents.sql`, à appliquer à la main). Les PDF sont dessinés dans le navigateur (jsPDF) : `js/famille-documents.js` (`KkFamilleDocs.publier`) les dépose à la contresignature (`publierPdfContrat`, `js/pages/contrats/03-part.js`) et à l'envoi du devis (`publierPdfDevis`, `js/pages/inscriptions/04-part.js`), boutons « Espace famille » pour les republier. L'edge function relie contrat = `contrats.enfant_id`, devis = `contrats.devis_id`, et signe l'ouverture (action `document`, 2 min). Fermetures = `etablissements.jours_fermeture` + `reseau_config.jours_fermeture_reseau` ; menu = lien vers `menu.html?c=<crèche>` ; règlement intérieur = texte du modèle `reglement_medicaments` recopié dans `espace-famille.js` (à garder en phase avec Documents et `famille.js`).
- Présentation : 4 onglets (Accueil = dernier message + code de pointage + prochaine fermeture, Infos = messages repliables, Documents = PDF + règlement intérieur + dépôt, Crèche = contacts et fermetures ; le menu est la tuile « Menu » de l'accueil ; `rendre()`, `js/pages/espace-famille.js`). Contacts : coordonnées de la crèche (`etablissements.telephone`/`email`, `creches.addr`, horaires) + personnes saisies dans Paramètres, `etablissements.contacts_famille` (directeur de la crèche) et `reseau_config.config.contacts_famille_reseau` (coordinateur, gestionnaire) — `sql/espace_famille_contacts.sql`, appliqué ; rien n'est déduit des comptes `referents` (pas d'e-mails personnels publiés).
- Installation et accès facilité : `manifest-famille.json` (PWA, icônes `icon-192/512.png`) ; carte « Retrouver cet espace facilement » sur l'accueil (`carteAppareil`, `js/pages/espace-famille.js`) = installation (`beforeinstallprompt`, aide iPhone) + code gardé en `localStorage` (`kk_famille_code`) **seulement avec l'accord de la famille** (case sur le formulaire du code, ou bouton) ; sans `?t=`, ce code rouvre une session courte (`SessionLien` inchangé : 15 min / 2 h). Effacé si l'accès est révoqué ou introuvable.
- Les e-mails portant le lien (contrat signé, renvoi du lien) demandent de **ne pas répondre avec des documents** : dépôt dans l'espace, onglet Documents ; l'adresse de réponse n'y est donnée que pour les questions. Tous les e-mails aux familles (dossier, pièces, code image, visite, code du contrat) ont `replyTo: a.janin@koalakids.fr` : sans cela les réponses arrivent sur le compte Gmail d'envoi (`koalakids.app@gmail.com`). Dossier, pièces et code image portent aussi la mention « pas de documents par e-mail » ; la confirmation de visite et le code du contrat non (la visite invite à répondre, le code n'a rien à déposer).
- Renvoi du lien par e-mail : « Code ou lien perdu ? » sur le formulaire du code (`renvoyerLien`) → edge function `renvoyer-lien-famille` (`--no-verify-jwt`, SMTP Gmail, ajoutée à `deploy-functions.yml`) : adresse retrouvée dans `enfants_parents.email`, envoi à cette seule adresse des accès **actifs**, réponse toujours neutre ; 3 demandes / h / adresse, 10 / h / IP (`famille_renvois`, empreinte SHA-256, `sql/espace_famille_renvoi_lien.sql`, à appliquer à la main).
- Notifications push famille : `famille_push` (abonnement par appareil, rattaché à `famille_acces`, 5 appareils max, supprimé avec l'accès ; `sql/espace_famille_push.sql`, à appliquer à la main) ; abonnement par les actions `push_abonner`/`push_desabonner` de l'edge function `espace-famille` (hôtes de push en liste blanche) ; envoi par `notify-push` avec `acces_ids` (accès actifs seulement), déclenché par `mfPrevenir` (`js/pages/demandes/18-messages-familles.js`) à la publication d'une information. Silence réseau : rien n'est envoyé ni retenu (comme les employés). Bouton dans la carte « Retrouver cet espace facilement » ; activer les notifications garde aussi l'accès sur l'appareil (la notification ouvre `espace-famille.html` sans code). iPhone : seulement si l'espace est installé.
- Côté crèche : encadré dans fiche enfant › Parents (`js/enfants/04-espace-famille.js`) et bouton « Information aux familles » (`js/pages/demandes/18-messages-familles.js`).

## Album photos
- Tuile « Album photos » (Demandes › Enfants & suivi, `main-album`, `js/pages/demandes/20-album-photos.js`, préfixe `alb`) : photos de la crèche classées par enfant, **tri manuel** (sélection de plusieurs photos puis clic sur l'enfant ; tri par visage en option, voir plus bas). Direction = toutes les crèches, référent·e = la leur.
- `sql/album_photos.sql` (à appliquer à la main, une partie à la fois) : tables `album_photos`, `album_photos_enfants` (une photo de groupe = une seule ligne stockée, un lien par enfant), `album_journal` (ajout, classement, retrait, suppression, remise ; sans UPDATE, lecture direction) et bucket privé `album` (chemin `<creche_id>/<photo_id>.jpg` + `_mini.jpg`, filtré par `kk_acces_album`). Photos réduites dans le navigateur (1600 px, miniature 360 px).
- Doublons : `albAjouter` calcule le SHA-256 du fichier d'origine (`albEmpreinte`), le compare aux `album_photos.empreinte` de la crèche et au lot en cours, puis demande d'ignorer ou d'ajouter quand même (fichiers strictement identiques seulement ; photos antérieures sans empreinte non comparées). `sql/album_photos_empreinte.sql` (à appliquer à la main).
- Départ définitif : « Départ : remise aux parents » = dossier .zip (JSZip), remise confirmée, puis suppression ; les photos où l'enfant est seul sont effacées, les photos de groupe restent chez les autres enfants (lien retiré). **Aucune archive conservée** (les photos sont données aux parents). Le droit à l'image est signé à l'entrée (papier, pas de champ en base) ; le scan se **importe** dans l'album de l'enfant (`albDroitAjouter`, encadré « Droit à l'image ») : `enfants_documents_admin` avec `piece_key = 'droit_image'`, bucket `documents-admin`, visible aussi dans « Autres documents importés » de la fiche enfant. Pas de nouvelle table ni de SQL.
- Tri par visage (étape 2, option **désactivée par défaut**, activée par la direction par crèche : `creches.tri_visage`, seuil `tri_visage_seuil`, RPC `kk_album_reglage_visage`) : `js/pages/demandes/21-album-tri-visage.js` (préfixe `albv`), `sql/album_tri_visage.sql` (à appliquer à la main après `album_photos.sql`). **Circuit fermé** : bibliothèque `@vladmandic/face-api` (MIT) et modèles hébergés dans `vendor/face-api/` (tiny face detector + landmarks tiny + reconnaissance), calcul dans le navigateur, aucune photo envoyée à un service extérieur. Seule l'**empreinte** (128 nombres, `album_references`) d'une photo de référence est enregistrée, et seulement pour un enfant ayant un **accord distinct du droit à l'image** (`album_visages_accord`, la RLS refuse une référence sans accord ; retirer l'accord efface références et propositions par déclencheur). Les visages des autres enfants d'une photo ne sont jamais enregistrés. `albvAnalyser` compare chaque visage au plus proche des références de chaque enfant (distance ≤ 0,52, écart ≥ 0,04 avec le deuxième enfant) ; score = (0,75 − d)/0,45 ; au-dessus du seuil la photo est classée seule, sinon une proposition (`album_propositions`) attend validation. Les photos viennent de Supabase (autre domaine) : `albvImage` charge les images en `crossOrigin='anonymous'`, sans quoi la détection reste bloquée (testé avec une image d'un autre domaine). Délais de sécurité sur le chargement du moteur, de la photo et de la détection ; repli sur le processeur si WebGL manque. À reprendre à la main au départ : `albvPurgerEnfant`. Fiabilité plus faible sur les bébés : privilégier 3 à 5 références et tester sur tablette avant de baisser le seuil.
- Accord **signé en ligne** par les parents (Espace famille) : document « Classement des photos par reconnaissance du visage » en carte orange « À signer » en haut de l'Accueil et de l'onglet Documents (`carteAccordVisage`, `accordSigner`, `js/pages/espace-famille.js`), affiché seulement si `creches.tri_visage` est vrai. Le texte et sa **version** vivent dans `supabase/functions/_shared/accord-visage.ts` (`ACCORD_VISAGE`, copie lisible `docs/album-accord-reconnaissance-visage.md`) : modifier le texte = changer `version` (une signature sur l'ancienne version est refusée, `texte_modifie`). Edge function `espace-famille` : `get` renvoie `accord_visage`, action `accord_visage` (nom prénom + nom, case autorité parentale, 5 signatures / h / accès) ; elle ajoute une ligne à `album_accords_signatures` (jamais modifiée : texte, hash SHA-256, nom saisi, date, empreinte IP) puis crée (`source='famille'`) ou supprime l'accord (`album_visages_accord`, le déclencheur efface alors références et propositions), journalise et prévient l'équipe (`signalerDepot`). `sql/album_accord_en_ligne.sql` (à appliquer à la main après `album_tri_visage.sql`). Côté crèche (onglet Références) : ligne « Signé en ligne par … » par enfant et bouton « Demander l'accord aux familles » (`albvDemanderAccord` : un message Espace famille + push par enfant sans réponse ayant un accès actif). La case manuelle reste pour l'accord papier (avertissement si un refus a été signé en ligne).

## Remise en température (Accès terrain)
- Tuile « Remise en température » (`js/pages/terrain-remise-temperature.js`) : fiche de contrôle 2023 des équipes, table `remise_temperature_journal` (`sql/remise_temperature.sql`, appliquée). Les plats du jour viennent de `menus_semaine` (bb6, bb18, grand, dédoublonnés ; plats froids décochés par `RT_FROID`) ; saisie en deux temps : T° de mise en chauffe (heure automatique, ligne enregistrée avec `temp_fin` vide = « en chauffe »), puis T° de fin de réchauffe qui complète la même ligne (UPDATE autorisé une seule fois, figé par le déclencheur `remise_temperature_fige`, `sql/remise_temperature.sql` partie 2 bis, appliquée). Conformité : 63 °C, en moins d'1 h ; observation obligatoire sinon. « Imprimer / PDF » produit la fiche de la semaine (lundi → vendredi). Le PMS (`pmsChargerRemise`, `js/pages/documents/07-pms-sanitaire.js`) lit ce registre : bloc à l'écran et tableau des 14 derniers jours dans le PDF (section 3, après le tableau HACCP). Archive mensuelle réservée à la direction (`pmsExporterMois` : PDF paysage par crèche ou toutes les crèches, CSV) ; conservation **3 ans** (règle HACCP), la table n'est jamais purgée.

- Paniers repas PAI : `rtChargerLignes` ajoute au service du jour un plat « Panier repas PAI — Prénom N. » (prénom + initiale du nom, `rtEnfantAbrege`, minimisation RGPD) par PAI actif avec `panier_repas` de la crèche (table `pai`), enregistré dans le même registre que les autres plats ; champ facultatif « Nom du plat apporté » (`rtN<i>`) ajouté au nom après « : ». Le rapprochement entre mise en chauffe et fin de réchauffe se fait par préfixe.
- Température du réfrigérateur (même tuile, bloc au-dessus du registre) : 3 relevés par jour (`matin`, `avant_four`, `soir`), table `frigo_temperature_journal` (`sql/frigo_temperature.sql`, à appliquer à la main), `js/pages/terrain-frigo.js` ; conforme ≤ 4 °C, observation obligatoire au-delà. Le PMS (`pmsChargerRemise`, `pmsFrigoLignes`) lit ce registre : tableau à l'écran sous le registre de remise en température et dans le PDF (section 3, 14 derniers jours) ; l'archive mensuelle (`pmsExporterMois`, `pmsMoisFrigo`) les reprend aussi (PDF : tableau par jour après les plats ; CSV : second tableau).

## Accès terrain par code image (option par crèche)

La direction est refusée (`code_direction`) : elle garde e-mail + mot de passe + double authentification.
